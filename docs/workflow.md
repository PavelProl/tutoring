# Работа от issue до GitHub

Согласовано 16.11.2026. Применяется со следующей новой Темы. Существующие Комплекты и их PDF автоматически не переделываются. Подготовка Комплекта — по скиллу `lesson-kit`; требования к выдаче — в [lesson-output.md](lesson-output.md).

## Рабочие копии

Основные `tutoring` и `tutoring-content` остаются на `main`. Работу выполняй в паре worktree: `chemistry/.worktrees/<issue-or-name>/tutoring` и `tutoring-content`. Так относительные ссылки между репозиториями сохраняются. Оригиналы — в `chemistry/tutoring-sources`; путь к ним определяй от корня проекта chemistry, а не от глубины worktree.

После подтверждения сохранности изменений в GitHub удали чистые временные worktree штатной командой Git. Сломанные связи сначала восстанови и сверь файлы; уникальные коммиты сохраняй. Наличие старой ветки само по себе не доказывает наличие потерянного изменения: оно могло попасть в main через squash.

Учёт учеников отложен. Заготовка tutoring-students удалена после проверки; не создавай её при подготовке Комплектов. Формат и место будущего учёта согласуются в отдельном issue; персональные данные остаются вне git. Роли каталогов и согласованное хранение оригиналов описаны в README.

## Выбор и запуск работы

Приоритеты, очередность и отложенные идеи ведём только в [плане](plan.md). Issue нужен, когда у результата есть отдельный статус, препятствие, приёмка или связанный PR. В описании держи один проверяемый результат, актуальный остаток и критерии завершения. Комментарии сохраняют историю, поэтому при расхождении сверяй текущее описание и статус. Обновляй карточку на контрольных точках: начало, препятствие, передача, завершение.

Метки возможностей и состояния независимы:

| Метка | Значение |
|---|---|
| `afk` | Агент способен выполнить согласованный объём самостоятельно |
| `hitl` | Нужны решения или приёмка автора |
| `ready` | Есть конкретный объём, входы доступны, обязательные зависимости сняты |
| `blocked` | Названы недостающий вход, решение, приёмка или незавершённая обязательная зависимость |
| `deferred` | Работа сохранена, но запуск отложен до явного запроса |
| `in-progress` | Issue действительно выполняется в указанном чате/worktree |
| `superseded` | Исторический объём заменён решением или другой работой; ссылка и причина сохранены |

`ready`, `blocked`, `deferred` и `in-progress` не ставятся одновременно. Частичное выполнение отражается в чек-листе; закрытие — состоянием GitHub, а не меткой `ready`. С закрытого issue снимаются рабочие метки. Незакрытые пункты исторического issue сверяются с фактами: выполненное отмечается с доказательством, отменённое объясняется, действующий остаток переносится со ссылкой в открытый issue. Сам по себе старый чек-лист не требует переоткрытия.

Обязательная зависимость записывается в обеих связанных карточках как «blocked by / blocks» с условием снятия. Рекомендуемый порядок не превращается в обязательную зависимость. Подготовка источников завершается до Конспекта; реализация формата выдачи — до выпуска в этом формате. Это независимые барьеры. Приоритет определяется ближайшим согласованным занятием, риском потери работы и готовностью входов; широкое чтение не вытесняет подготовку нужного Комплекта.

При школьной подготовке без экзамена сверка ФИПИ и полная карта 10–11 классов не становятся обязательными барьерами. Общие инструменты проверки могут сокращать ручную работу, но их отсутствие не подменяется ложным статусом «готово»: до реализации выполняются и фиксируются отдельные проверки. Обязательны конкретные входы и проверки результата, а не закрытие всего отложенного backlog.

Работу запускает явное поручение автора в чате. Агент сверяет план, открытые `in-progress`, актуальное описание и последнюю передачу связанного issue, при необходимости — PR. При нескольких `in-progress` перечисляет их и уточняет, какой продолжать. Если работа ведётся в issue, перед началом ставит `in-progress`, снимает прежнюю рабочую метку и отмечает чат и ветку. Следующий этап выбирают по плану в пределах поручения автора.

`afk`, порядок в таблице, открытие PR и комментарий передачи не создают фоновую работу. Автоматический запуск можно обещать только после отдельной настройки и проверки диспетчера; он должен иметь явный триггер, предел расхода, блокировку повторного запуска и правило остановки на `hitl`/`blocked`. Параллельная работа требует отдельного согласования.

Если нужное issue создать не удалось, сообщи об ограничении и сохрани согласованный объём в рабочей ветке. Свяжи его с отдельным issue после восстановления доступа.

## Начало и сохранение работы

1. Выбери один согласованный результат по плану. Если у него есть issue, веди работу в этой карточке. При сверке процесса можно проверять несколько связанных карточек.
2. Сделай `git fetch` в обоих репозиториях. Сверь новые AGENTS, GLOSSARY и docs в основной ветке. При недоступном fetch зафиксируй это; отдельно проверь разрешённые команды GitHub. Отказ общей сетевой пробы или gh auth status не доказывает недействительность токена либо недоступность всех команд. Если issue создать невозможно, явно сообщи препятствие; не выдавай локальную подготовку за зарегистрированную работу в GitHub.
3. Сначала локально подготовь Конспект и пару PDF, передай автору на проверку и внеси замечания. После утверждения итоговой версии агент самостоятельно создаёт логические коммиты, отправляет ветки, открывает/завершает PR и обновляет документацию. Перед коммитом сообщает ветку, файлы и суть; отдельного разрешения на рутинные git-действия не требуется.
4. Промежуточные версии содержания хранятся локально с `draft` / `verified: false`; не создавай отдельные коммиты и PR на каждую правку по ходу приёмки. Ранее созданный черновой PR можно завершить после утверждения. Платное содержание и данные учеников не попадают в публичный tutoring.

## Проверка и завершение

Агент сверяет содержание с подготовленной базой, пересчитывает расчёты и баланс используемых уравнений, проверяет методическую последовательность и вёрстку. Отдельный проверяющий агент и полное повторное чтение книг не запускаются. Существенное противоречие сначала исследуется по источникам; неразрешённое — вопрос автору и остановка выпуска.

Автор просматривает итоговые PDF. Только после явного подтверждения проверенного объёма агент меняет соответствующие статусы и публикует PDF как готовые. Проверка одного Комплекта не подтверждает весь банк или остальные Комплекты Темы.

Если автор позднее подтверждает завершение исторической итерации, запиши это в её issue и карте курса. Закрой подтверждённый результат, а неиспользуемый исторический остаток вынеси со ссылкой в отложенный issue. Не требуй заново приёмку уже завершённой итерации и не распространяй подтверждение на весь банк либо отдельные проверки. При запрете менять старые учебные файлы сохрани их метаданные и явно объясни границу подтверждения в issue.

Технические изменения агент проверяет тестами/запуском по их смыслу. Содержание объединяется после приёмки автором; агент завершает связанные PR и синхронизацию самостоятельно в рамках выданного поручения. Отправленный черновик, открытый PR и объединённый PR — разные состояния доставки. Чек-лист отмечается по мере появления доказательств; в PR указываются проверки и связь с issue обоих репозиториев.

Перед закрытием issue проверь:

- локальные изменения сохранены; нужные коммиты присутствуют в удалённых ветках;
- PR обоих репозиториев связаны с issue; требуемые изменения попали в main;
- технические проверки пройдены; обязательная для результата авторская приёмка содержания явно подтверждена с указанием версии и объёма; неполученная приёмка оставляет issue открытым и `blocked`;
- исходники, ссылки, карта курса и сведения об источниках согласованы;
- в изменённой документации проверены локальные ссылки и структура таблиц (число столбцов и отсутствие посторонних строк); если карту читает сборщик, подтверждена неизменность вывода существующих Комплектов;
- временные копии можно убрать без потери изменений.

Чистый `git status` и совпадение с кешированным origin/main не доказывают синхронизацию. Подтверди её сравнением SHA с живым GitHub после fetch либо через разрешённый gh pr view: состояние MERGED, ожидаемый merge/head SHA и наличие результата в локальном main. Поле baseRefOid старого PR не доказывает текущую вершину main. Укажи способ и предел проверки; не называй проверку PR выполненным fetch. Обычный push main допустим только как fast-forward с нужным объёмом и после проверок, без force; отказ или конкурирующие изменения требуют новой сверки, а не перезаписи. При сетевой ошибке оставь issue открытым и перечисли неотправленные или непроверенные изменения.

Если результат зависит от двух репозиториев, не закрывай issue после доставки только одного. `Closes #N` используй только когда объединение этого PR действительно завершает все критерии; иначе — `Refs #N`. После подтверждённой доставки закрой issue, сними `in-progress`/прочие рабочие метки и запиши итог проверки. Удали чистые worktree штатной командой Git только после проверки tracked, untracked и ignored файлов и сохранности уникальных изменений; затем убери ненужные локальные ветки. При squash сравнивай патчи, а не только ancestry. Удаление удалённой ветки — после подтверждения её сохранности и отсутствия открытого PR; сомнительное оставь с явным учётом.

Перед сменой чата запиши в связанном issue: сделано / проверки и подтверждённые SHA/PR / оставшийся объём и препятствия / следующее действие в рамках этого issue / открытые вопросы. Если работа остановлена, сними `in-progress` и поставь соответствующее состояние. Если GitHub недоступен, сохрани согласованный результат в рабочей ветке и сообщи её путь и неподтверждённые действия. Если отдельного issue нет, ход небольшой работы виден из рабочей ветки и результата проверки.
