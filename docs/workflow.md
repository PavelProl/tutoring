# Работа от issue до GitHub

Согласовано 16.11.2026. Применяется со следующей новой Темы. Существующие Комплекты и их PDF автоматически не переделываются. Подготовка Комплекта — по скиллу `lesson-kit`; требования к выдаче — в [lesson-output.md](lesson-output.md).

## Где хранится информация

| Место | Назначение |
|---|---|
| README | Цели, запуск и навигация |
| AGENTS | Короткие обязательные правила и ссылки на процессы |
| GLOSSARY | Термины |
| Скиллы | Порядок повторяемой работы со ссылками на требования |
| Инструкции в docs | Требования к чтению и написанию содержания |
| tutoring-content/course-map.md | Порядок, содержание и зависимости Тем; краткая готовность со ссылками |

| GitHub Issues | Ход работы, проверки, препятствия, следующие действия и связанные PR обоих репозиториев |
| ADR и journal | Причины решений и существенные уроки; исторические записи не описывают текущий статус |

Отдельные постоянные отчёты перед коммитом не создаются: результаты проверок записываются в issue и PR. Технические ограничения сборщика описываются в README, требования к будущему поведению — в lesson-output.md.

## Рабочие копии

Основные `tutoring` и `tutoring-content` остаются на `main`. Работу выполняй в паре worktree: `chemistry/.worktrees/<issue-or-name>/tutoring` и `tutoring-content`. Так относительные ссылки между репозиториями сохраняются. Оригиналы — в `chemistry/tutoring-sources`; путь к ним определяй от корня проекта chemistry, а не от глубины worktree.

После подтверждения сохранности изменений в GitHub удали чистые временные worktree штатной командой Git. Сломанные связи сначала восстанови и сверь файлы; уникальные коммиты сохраняй. Наличие старой ветки само по себе не доказывает наличие потерянного изменения: оно могло попасть в main через squash.

Учёт учеников отложен. Для подготовки Комплектов папка tutoring-students не требуется; персональные данные, когда появятся, остаются вне git.

## Начало и сохранение работы

1. Найди или создай issue с одним проверяемым результатом и чек-листом; поставь `in-progress`. Один чат ведёт один issue.
2. Сделай `git fetch` в обоих репозиториях. Сверь новые AGENTS, GLOSSARY и docs в основной ветке. При недоступном fetch зафиксируй это; отдельно проверь разрешённые команды GitHub. Отказ общей сетевой пробы или gh auth status не доказывает недействительность токена либо недоступность всех команд. Если issue создать невозможно, явно сообщи препятствие; не выдавай локальную подготовку за зарегистрированную работу в GitHub.
3. Агент самостоятельно создаёт логические коммиты, отправляет рабочие ветки и открывает PR после соответствующих проверок. Перед коммитом сообщает ветку, файлы и суть; отдельного разрешения на рутинные git-действия не требуется.
4. Черновое содержание можно сохранять и отправлять в приватный tutoring-content с `draft` / `verified: false`. Отправка в GitHub не означает химическую проверку. Платное содержание и данные учеников не попадают в публичный tutoring.

## Проверка и завершение

Агент сверяет содержание с подготовленной базой, пересчитывает расчёты и баланс используемых уравнений, проверяет методическую последовательность и вёрстку. Отдельный проверяющий агент и полное повторное чтение книг не запускаются. Существенное противоречие сначала исследуется по источникам; неразрешённое — вопрос автору и остановка выпуска.

Автор просматривает итоговые PDF. Только после явного подтверждения проверенного объёма агент меняет соответствующие статусы и публикует PDF как готовые. Проверка одного Комплекта не подтверждает весь банк или остальные Комплекты Темы.

Технические изменения агент проверяет тестами/запуском по их смыслу. Содержание объединяется после приёмки автором; агент завершает связанные PR и синхронизацию самостоятельно в рамках выданного поручения.

Перед закрытием issue проверь:

- локальные изменения сохранены; нужные коммиты присутствуют в удалённых ветках;
- PR обоих репозиториев связаны с issue; требуемые изменения попали в main;
- технические проверки пройдены, авторская приёмка содержания подтверждена либо явно остаётся открытой;
- исходники, ссылки, карта курса и сведения об источниках согласованы;
- временные копии можно убрать без потери изменений.

Чистый `git status` и совпадение с кешированным origin/main не доказывают синхронизацию. Подтверди её сравнением SHA с живым GitHub после fetch либо через разрешённый gh pr view. Укажи, какой способ использован; не называй проверку PR выполненным fetch. При сетевой ошибке оставь issue открытым и перечисли неотправленные или непроверенные изменения.

Перед сменой чата запиши в issue: сделано / дальше / открытые вопросы. Если GitHub недоступен, сохрани согласованный результат в рабочей ветке и сообщи её путь и неподтверждённые действия. Не создавай отдельный файл текущего статуса.
